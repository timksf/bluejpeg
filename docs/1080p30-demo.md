# 1080p30 demonstration

Split-clock variant of the [DDR3/UDP system](udp-system.md), built with
`make -C hdl bitstream SYSTEM=udp UDP_DEMO_200=1`. It encodes 1920 × 1080 4:4:4 at over 30 fps with
the encoder at 200 MHz. Frames are preloaded into DDR3 and replayed, since raw 1080p30 needs
1.493 Gb/s and the loader only accepts data while the encoder is idle.

## Clock domains

| Domain | Frequency | Contents |
| --- | ---: | --- |
| Encoder | 200 MHz | Tiler, JPEG pipeline, encoder registers |
| DCT | 25 MHz | DCT, connected to the encoder clock through timed gearboxes |
| System | 125 MHz | UDP, frame control, DDR requests, packetizer, MDIO |
| Memory | 81.25 MHz | MIG AXI interface |

`BlueJPEGClockCrossing` presents the encoder interface in the system domain.

- Pixels and JPEG bytes cross in asynchronous FIFOs with all AXI4-Stream side-band signals
- AXI4-Lite write address and data are paired before crossing, responses return after the encoder
  transaction completes
- A frame start is retried until the encoder reports busy, and a completion token returns when busy
  falls, so system-side busy covers the whole handshake
- Busy and interrupt pass through two-stage synchronizers

`UdpMemoryCdc` crosses the five AXI channels independently and keeps bursts, IDs and ordering. All
domains, including MIG and JTAG, share one reset source and release their resets locally, and loss
of PLL lock also resets the MIG. Bluespec `SyncFIFO` requires this, since it resets both sides from
its source reset.

The CDC constraints cover the pointer and status synchronizers, limit Gray-pointer transit and bus
skew to 5 ns and constrain FIFO payload paths with a head register. Encoder, DCT and transmit clocks
stay timed against each other. Vivado's remaining CDC findings (`SyncFIFO` reset pins CDC-7, JTAG
handshake, MIG reset) are covered by the common reset.

## Validation in simulation

`TbJpegUdpDemo` uses the board's 200, 125 and 25 MHz clock ratio and an independently phased 80 MHz
memory model. It loads and verifies a frame, then encodes three frames and checks bytes, side-bands,
packet numbering, repeat stop, interrupts, checksums and AXI burst boundaries. The frame period must
stay within 4,166,666 system cycles (30 fps at 125 MHz). It measures 3,914,029 cycles (31.94 fps)
without output stalls.

```sh
make -C hdl sim RUN_TEST=TbJpegUdpDemo UDP_TEST_1080P=1 BUILDDIR=build/demo1080
make -C hdl sim RUN_TEST=TbUdpPacketizer
```

## Hardware results

The routed design meets timing at 200 MHz with near-zero setup margin and +0.040 ns hold slack. If the
first route misses setup, the build runs physical optimization and a targeted reroute. It writes no
bitstream if setup, hold or bus-skew checks fail.

| Measurement | Result |
| --- | ---: |
| Frame period | 3,912,750 cycles at 125 MHz, 31.302 ms |
| Frame rate | 31.947 fps on the FPGA, 31.945 fps received by the host |
| JPEG size | 290,450 bytes in 284 UDP packets |
| Encoder output stalls | 0 |

All 100 frames of a recorded run and 2,618 frames of a live preview matched the C++ reference, with no
protocol errors.

A sequence of 30 FFmpeg `testsrc2` frames (248,832,000 bytes) was replayed from DDR3 for over 2,900
frames at 31.948 fps, with the host setting `BASE` ahead of the reader and each JPEG hash checked
against its position in the sequence. Loading takes about two seconds per frame.

## Running the demonstration

Use the session script `bluejpeg_udp_demo_jlink.tcl` (125 MHz counters and MDC divider). Load the
frame and start the receiver before enabling repeat.

```sh
openocd -f hdl/test/host/udp/bluejpeg_udp_demo_jlink.tcl
python3 hdl/test/host/udp/recv_jpeg.py --output demo-rx --expect hdl/build/demo1080/udp_capture.jpg --count 100
python3 hdl/test/host/udp/load_frame.py assets/sample_1920x1280.bmp
```

```tcl
bluejpeg_udp_repeat pa200t.tap 1
bluejpeg_udp_repeat pa200t.tap 0
bluejpeg_udp_report pa200t.tap
```

REPEAT runs unpaced. `preview_jpeg.py` checks every JPEG against the reference and shows the stream in
`ffplay` with a frame number overlay (`--no-overlay` to disable). `load_pattern.py` prepares the
animated sequence.

```sh
python3 hdl/test/host/udp/preview_jpeg.py --expect hdl/build/demo1080/udp_capture.jpg
python3 hdl/test/host/udp/load_pattern.py --frames 30 --output pattern
python3 hdl/test/host/udp/preview_jpeg.py --sequence pattern/sequence.json --no-overlay
```
