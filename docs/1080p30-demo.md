# 1080p30 demonstration

The split-clock variant of the [DDR3/UDP system](udp-system.md) encodes 1920 × 1080 YCbCr 4:4:4
frames at more than 30 frames per second on the PA200T board. It is built with
`make -C hdl bitstream SYSTEM=udp UDP_DEMO_200=1` and separates the encoder from the rest of the
system, so the encoder runs at 200 MHz while UDP, frame control and memory keep their own clocks.
Frames are preloaded into DDR3 and replayed, because raw 1080p30 input needs 1.493 Gb/s before
packet overhead, more than the Gigabit link carries, and the loader only accepts data while the
encoder is idle.

## Clock domains

| Domain | Frequency | Contents |
| --- | ---: | --- |
| Encoder | 200 MHz | Tiler, JPEG pipeline, encoder registers |
| DCT | 25 MHz | DCT, connected to the encoder clock through timed gearboxes |
| System | 125 MHz | UDP, frame control, DDR requests, packetizer, MDIO |
| Memory | 81.25 MHz | MIG AXI interface |

`BlueJPEGClockCrossing` presents the encoder's interface in the system domain. Pixels and JPEG bytes
cross in asynchronous FIFOs that carry all AXI4-Stream side-band signals. AXI4-Lite write address and
data are paired before they cross, and read and write responses return only after the transaction
has completed in the encoder domain. A frame start is retried in the encoder domain until the encoder
reports busy, and a completion token returns once busy falls, so the system-side busy covers the whole
handshake. Busy and interrupt levels pass through two-stage synchronizers.

`UdpMemoryCdc` crosses the five AXI memory channels independently and keeps burst fields, IDs,
ordering and responses. DDR3 calibration is synchronized into the system domain. All transaction
domains, including MIG and JTAG, share one reset source and release their resets locally, and a loss
of PLL lock also resets the MIG, so no outstanding transaction survives a reset of only the bridges.
This common reset is a requirement of the Bluespec `SyncFIFO`, which resets both sides from its
source reset.

The CDC constraints mark the pointer and status synchronizers, limit Gray-pointer transit and bus
skew to 5 ns and constrain FIFO payload paths that have an explicit head register. They target
these crossings only, and the encoder, DCT and transmit clocks remain timed against each other.
Vivado's CDC report still lists the `SyncFIFO` destination reset pins (CDC-7) and the existing JTAG
handshake and MIG reset findings, which are covered by the common reset described above.

## Validation in simulation

`TbJpegUdpDemo` runs the system with the exact 200 to 125 to 25 MHz ratio of encoder, system and DCT
clock and an independently phased 80 MHz memory model, slightly slower than the board's MIG. It loads
a frame over UDP, including a duplicate and a malformed datagram, preloads the rest of the frame,
verifies it, and encodes three consecutive frames. Each is compared byte for byte with the C++
reference, together with stream side-bands, packet and frame numbering, repeat stop, interrupt
handling, memory checksums and AXI burst boundaries. The test requires a frame period of at most
4,166,666 system cycles, the 30 fps budget at 125 MHz, and passes with 3,914,026 cycles, or 31.94
frames per second, without output stalls.

```sh
make -C hdl sim RUN_TEST=TbJpegUdpDemo UDP_TEST_1080P=1 BUILDDIR=build/demo1080
make -C hdl sim RUN_TEST=TbUdpPacketizer
```

## Hardware results

The routed design meets timing at 200 MHz with essentially no setup margin to spare and +0.040 ns
hold slack, without failing endpoints. The build script adds physical optimization and a targeted
reroute of critical nets if the first route misses setup, and refuses to write a bitstream if setup,
hold or bus-skew checks fail.

| Measurement | Result |
| --- | ---: |
| Frame period | 3,912,750 cycles at 125 MHz, 31.302 ms |
| Frame rate | 31.947 fps on the FPGA, 31.945 fps received by the host |
| JPEG size | 290,450 bytes in 284 UDP packets |
| Encoder output stalls | 0 |

All 100 captured frames of a recorded run matched the C++ reference byte for byte, and another 2,618
consecutive frames passed the same check in the live preview. Protocol error counters stayed at zero
and the MAC reported only good frames.

An animated sequence of 30 distinct FFmpeg `testsrc2` frames, each with its frame number drawn in,
was loaded into DDR3 after the static frame (248,832,000 bytes) and replayed for more than 2,900
frames at 31.948 fps. Control software selects the next DDR address ahead of the reader, and the
hash of each JPEG must match its position in the sequence on every loop, with all 30 hashes distinct.
Loading takes about two seconds per frame, which is preload time, not playback rate.

## Running the demonstration

The demonstration uses the session script `bluejpeg_udp_demo_jlink.tcl`, which counts in 125 MHz
system cycles and sets the MDC divider for that clock. Load the frame and start the receiver before
enabling repeat.

```sh
openocd -f hdl/test/host/udp/bluejpeg_udp_demo_jlink.tcl
python3 hdl/test/host/udp/recv_jpeg.py --output demo-rx --expect hdl/build/demo1080/udp_capture.jpg --count 100
python3 hdl/test/host/udp/load_frame.py assets/sample_1920x1280.bmp
```

```tcl
bluejpeg_udp_repeat pa200t.tap 1
bluejpeg_udp_repeat pa200t.tap 0
bluejpeg_udp_report pa200t.tap
```

REPEAT runs as fast as the system allows instead of pacing to exactly 30 Hz. `preview_jpeg.py` shows
the stream in a 1280 × 720 window through `ffplay`, checks every JPEG against the reference before it
adds a small overlay with frame number and receive rate, and stops repeat when the window closes. The
animated sequence is prepared and played with `load_pattern.py` and the `--sequence` option of the
preview, where `--no-overlay` shows the encoded frames unchanged.

```sh
python3 hdl/test/host/udp/preview_jpeg.py --expect hdl/build/demo1080/udp_capture.jpg
python3 hdl/test/host/udp/load_pattern.py --frames 30 --output pattern
python3 hdl/test/host/udp/preview_jpeg.py --sequence pattern/sequence.json --no-overlay
```
