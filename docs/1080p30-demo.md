# 1080p30 DDR3/UDP demonstration

The experimental board variant uses a 200 MHz encoder, 25 MHz DCT, 125 MHz
UDP/control domain, and the existing 81.25 MHz MIG interface. Full-HD split-clock simulation passes at **31.94 fps equivalent**. The integrated
route passes with **0.000 ns setup WNS** and **+0.040 ns hold WHS**, with no failing
setup or hold endpoints. The user-approved image is loaded into FPGA SRAM and
the live hardware demonstration runs at **31.95 fps**. Flash was not written.
The reported setup margin is effectively zero.

The demonstration supports a single preloaded 1920 × 1080 YCbCr 4:4:4 raster
and an animated FFmpeg sequence in DDR3. The current live preview replays 30
distinct `testsrc2` frames. Each image is JPEG-encoded by the FPGA and returned
over UDP. Measurements include the complete encoder-to-UDP repeat period and
the final packet handshake. Raw three-byte 1080p30 input requires 1.493 Gb/s before packet overhead,
exceeding the board's 1 GbE link. The existing loader requires encoding to be idle,
so moving full-HD input is preloaded and replayed rather than uploaded continuously.

## Clock domains and crossings

`UDP_DEMO_200=1` selects the split-clock DDR3 variant. The original 81.25 MHz DDR3
and 83.333 MHz BRAM variants remain available without this flag.

| Domain | Frequency | Work |
| --- | ---: | --- |
| Encoder | 200 MHz | Tiling, JPEG pipeline, encoder registers |
| DCT | 25 MHz | DCT, with timed related-clock gearboxes to the encoder |
| System | 125 MHz | UDP, frame control, DDR requests, packetizer, MDIO |
| Memory | 81.25 MHz | MIG AXI interface |

`BlueJPEGClockCrossing` presents the encoder interface in the system domain.
Pixels and JPEG bytes use asynchronous FIFOs carrying all AXI-Stream sidebands.
AXI-Lite write address/data are paired before crossing. Read and write responses
return only after the actual encoder-domain transaction completes. A start token
is retried locally until the encoder asserts busy, and a completion token returns
after busy falls. System busy remains asserted throughout this handshake. Busy
and IRQ levels use two-stage synchronizers.

`UdpMemoryCdc` crosses all five AXI memory channels independently, retaining burst
fields, IDs, ordering and responses. Calibration is synchronized to the system.
All transaction domains share a reset epoch including MIG and JTAG, with local
reset release for the surrounding logic in each domain. PLL lock loss also resets
MIG so outstanding transactions cannot survive a reset of only the bridges.

The CDC constraints mark pointer and status synchronizers, bound Gray-pointer
transit and bus skew to 5 ns, and bound FIFO payload paths where an explicit head
register exists. Exceptions target those crossings rather than globally disabling
timing between application clocks. Encoder/DCT and GTX/GTX90 remain timed.
The implementation generates CDC, clock-interaction and bus-skew reports for review.

The automatic CDC report is not empty. The standard Bluespec `SyncFIFO` primitive
uses its source reset for both sides. Vivado reports CDC-7 on each destination
`dNotEmptyReg` reset pin, despite recognizing the two-stage pointer synchronizers.
These reset findings require the common-epoch contract above, rather than
independent reset of either side. FIFO payload paths are clock-enable controlled
by synchronized pointers. Existing JTAG handshake and MIG reset/temperature-monitor
findings also remain visible in the report. No blanket CDC waivers are applied.

`UdpPacketizer` has a 2048-byte BRAM FIFO and a two-entry descriptor queue.
Collection proceeds while the preceding packet transmits. A descriptor is
published only after its full packet is stored. The existing eight-byte header,
1024-byte maximum JPEG payload, sequence numbering and completion at the final
UDP handshake are preserved. Full storage backpressures the encoder.

## Validation

`TbJpegUdpDemo` uses exact 200:125:25 MHz encoder/system/DCT ratios and an
independently phased 80 MHz memory model, slightly slower than the board's MIG.
Simulation periods are 10, 16, 80 and 25 units respectively. It checks three
consecutive JPEGs byte for byte against the C++ reference, including stream
sidebands, packet/frame sequencing, repeat stop, configuration acknowledgement,
IRQ assertion/clear, memory checksums and burst boundary rules. The default crop
of `assets/sample_1920x1280.bmp` produces 290,450 bytes in 284 packets per JPEG.
The 1080p test requires PERIOD <= 4,166,666 system cycles, the 30 fps budget at
125 MHz. It passes with PERIOD **3,914,026**, or **31.312 ms** and **31.936 fps**.
All three 290,450-byte frames match the reference, with OUTSTL = 0. This leaves
2.021 ms inside the 30 fps period. System counters and host reporting use 125 MHz.

The demo exercises UDP loading with one packet, a duplicate and a malformed
packet, then preloads the remainder through BDPI to avoid millions of single-write
round trips. Full-image verification and all encoding reads use AXI through the
memory bridge. `TestJpegUdpSystem` retains the full UDP-loading regression.
`TbUdpPacketizer` separately checks lengths 1, 1023, 1024, 1025, 2048 and 3073
with stalled output and overlapping collection/transmission.

### Hardware result and live preview

The SRAM image was loaded with user approval on 2026-11-15. DDR calibrated and
the PHY negotiated 1000 Mb/s full duplex. The 1920 × 1080 crop verified with
CHK1 `a8b8c3b7` and CHK2 `b4f30067` after one upload retry.

| Hardware measurement | Result |
| --- | ---: |
| PERIOD at 125 MHz | 3,912,750 cycles |
| Frame period | 31.302 ms |
| Hardware frame rate | 31.94684 fps |
| Host receive rate | 31.945 fps |
| JPEG size / UDP packets | 290,450 bytes / 284 |
| JPEG output stalls | 0 |

All 100 saved capture frames matched the C++ reference byte for byte. An additional
2,618 consecutive frames passed the same comparison in the live preview before
its shutdown behavior was tested. After clearing initial sticky events, protocol
errors stayed zero and MAC_EVENTS was `0x108`, containing only TX/RX good-frame
indicators. No MAC error bits or frame gaps were observed during that run.
Logs and completed-frame counters are under
`hdl/build/demo_validation/split_clocks/hardware/`.

With the OpenOCD demo session running and the raster already loaded, launch:

```sh
python3 hdl/test/host/udp/preview_jpeg.py --expect hdl/build/demo1080_split_clocks/udp_capture.jpg
```

The preview requires `ffplay`. It starts repeat and displays a 1280 × 720 window
of the full 1920 × 1080 image. A top-left host overlay shows the FPGA packet frame
number, received-frame count and measured receive FPS. The frame number changes
with each received FPGA frame. The JPEG bytes are checked before adding this
display overlay. It stores no frame sequence, so the preview can run continuously
without filling the disk. Closing its window stops repeat and waits for idle,
which was verified on hardware.

### Animated FFmpeg pattern

The user selected the currently running animated DDR replay. It uses 30 distinct
FFmpeg `testsrc2` frames with the source frame number drawn into the input before
FPGA encoding. A full-range planar YUV444 clip is converted to the loader's
interleaved pixel format. Each DDR frame is checksum-verified after upload.
The 30-frame clip occupies 248,832,000 bytes of DDR, with its first frame after
the original static raster so that raster remains available at BASE 0.

```sh
python3 hdl/test/host/udp/load_pattern.py --frames 30 --output /tmp/bluejpeg-pattern
python3 hdl/test/host/udp/preview_jpeg.py --sequence /tmp/bluejpeg-pattern/sequence.json --no-overlay
```

The loader measured about 2.05 seconds per full-HD input frame at a 0.4 ms packet
gap. This is preload time, not playback frame rate. Independent JTAG control
polls completed FPGA frames and selects the next DDR address ahead of the reader.
Display writes run separately from address scheduling. A missed control deadline
stops the demo, and each JPEG's hash must match its source position on subsequent
loops. All 30 JPEGs must also have distinct hashes. This caught the first attempt's
display-startup scheduling delay and passed after control was separated.

The animated hardware run sustained **31.948 fps** through more than 2,900 frames,
with all 30 replay positions verified repeatedly. A sampled PERIOD was 3,912,554
system cycles. Protocol errors and MAC error bits were zero. The `--no-overlay`
mode displays the actual FPGA-encoded test pattern without host telemetry.
Closing the window stops repeat. This pattern preview is left running.

The current manifest and logs are in
`hdl/build/demo_validation/split_clocks/hardware/pattern/`, with the active log
at `/tmp/bluejpeg-pattern-preview.log`. This is a repeating preloaded FFmpeg clip,
not a continuously uploaded raw 1080p30 feed.

```sh
nix develop ./nix
make -C hdl sim RUN_TEST=TbUdpPacketizer CXX_NO_OPT=
make -C hdl sim RUN_TEST=TestJpegUdpSystem CXX_NO_OPT=
make -C hdl sim RUN_TEST=TbJpegUdpDemo UDP_TEST_1080P=1 BUILDDIR=build/demo1080_split_clocks CXX_NO_OPT=
python3 -m unittest discover -s hdl/test/host/udp -p 'test_*.py' -v
make -C hdl bitstream SYSTEM=udp UDP_DEMO_200=1
```

No BlueCSR dependency patch is required. The pre-existing `dep/BSVTools`
modification was left intact. No commits were created.

The default experimental FPGA build is under
`hdl/build/BlueJPEG_PA200T_UDP_mig_200/BlueJPEG_PA200T_UDP/`.
The current reused-MIG project is `hdl/build/demo200_pll/BlueJPEG_PA200T_UDP/`.
The build uses additional physical optimization and a targeted critical-net
reroute when the first route misses setup timing. It refuses to write a bitstream
if final setup, hold or bus-skew checks fail or unresolved critical warnings remain.
Simulation throughput is image-dependent and is not a board measurement.

The passing image is
`hdl/build/demo_validation/split_clocks/replicate_route/bluejpeg_1080p30.bit`.
Its `routed.dcp`, `timing.rpt`, `paths.rpt`, `cdc.rpt`, `clocks.rpt`, `bus_skew.rpt`
and `vivado.log` are alongside it. The timing report has zero missing clocks and
zero unconstrained internal endpoints. `split_clocks/results.json` records the
measurements and bitstream hash. The directory name records an attempted driver
replication, which Vivado skipped. The targeted net reroute and subsequent
physical optimization produced the passing result without encoder RTL changes.

Earlier experiments ran the entire application at 200 MHz. Those simulation
counts and failed timing reports are superseded. Removed implementation
experiments are archived under `hdl/build/demo_validation/superseded_whole_system_200/`.

## Board procedure

The initial read-only probe found module ID 13 and no JPEG block. The user then
approved replacing that SRAM image. The loaded demo now reports SYS ID 3 and
JPEG ID 1. Its programming log is saved with the hardware results. The volatile
FT232H procedure is documented in [UDP bring-up](udp-system.md).

The demo J-Link session uses a 125 MHz performance-counter frequency and an MDC
divider of 125. Start the receiver before enabling repeat:

```sh
openocd -f hdl/test/host/udp/bluejpeg_udp_demo_jlink.tcl
python3 hdl/test/host/udp/load_frame.py assets/sample_1920x1280.bmp --write-crop /tmp/bluejpeg-1080.bmp
python3 hdl/test/host/udp/recv_jpeg.py --output /tmp/bluejpeg-demo --expect hdl/build/demo1080_split_clocks/udp_capture.jpg --count 100
```

```tcl
bluejpeg_udp_repeat pa200t.tap 1
bluejpeg_udp_repeat pa200t.tap 0
bluejpeg_udp_report pa200t.tap
```

Let the receiver finish its 100 frames before disabling repeat. Check the
hardware PERIOD counter, received frame rate, exact JPEG comparisons, frame and
packet gaps, and Ethernet error counters. REPEAT runs as fast as possible rather
than pacing to exactly 30 Hz.
